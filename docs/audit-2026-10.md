# Audit et refonte technique — octobre 2026

Revue complète du code (application Next.js, API, pipeline d'ingestion,
scripts Mac mini), avec mesures sur une base Postgres 16 réelle : la démo
(25 pièces), le catalogue `neon-catalog.sql` (265 pièces) et un catalogue
synthétique de 200 000 pièces / 100 000 cross-références / 266 000 offres.

## En bref

| Gravité | Constat | État |
|---|---|---|
| Critique | Toute mise à jour d'une pièce existante via `/api/ingest` échoue depuis le 14 juin | Corrigé |
| Critique | Une mise à jour efface description, catégorie, attributs, statut… | Corrigé |
| Critique | Next.js 15.5.19 (avis critiques), drizzle-orm < 0.45.2 (injection SQL) | Mis à jour |
| Haute | Recherche en scan complet : ~1,6 s par requête à 200k pièces, à chaque frappe | 2–7 ms |
| Haute | `/admin/*` accessible sans authentification | Corrigé |
| Haute | Filtres de `/recherche` sans effet au clic (navigation jamais appliquée) | Corrigé |
| Haute | Images Open Graph des fiches pièces toujours en erreur | Corrigé |
| Moyenne | Supersessions perdues quand le remplacement vient d'un lot précédent | Corrigé |
| Moyenne | Abonnements email collectés sans aucun envoi d'alerte | **À décider** |

Aucun test n'existait : 21 tests unitaires, 19 tests d'intégration sur
Postgres et une CI GitHub Actions couvrent désormais les points ci-dessus.

## 1. Constats critiques

### 1.1 Mises à jour d'ingestion en échec systématique

Depuis le commit `7beefa9` (ajout de `specs`), l'upsert d'une pièce
existante contenait `COALESCE(NULLIF(excluded.specs::text, '{}'), parts.specs)`
— un mélange `text` / `jsonb` que Postgres refuse
(`COALESCE types text and jsonb cannot be matched`). Conséquence : seules les
pièces **nouvelles** étaient enregistrées. Les modes `--update`, `--repair`
et `--clean` d'`accumulate.ts` renvoyaient 100 % d'erreurs (HTTP 207), sans
que rien ne soit écrit.

### 1.2 Mises à jour destructrices (masquées par 1.1)

Avant ce commit — et de nouveau si 1.1 avait été corrigé seul — une
ré-ingestion écrasait :

- `description`, `category`, `attributes` par `null` quand le lot ne les
  fournit pas. Le prompt du mode `--update` ne demande **pas** de
  description : un cycle complet aurait vidé les descriptions du catalogue ;
- `status` par `unknown` si absent, et un statut prouvé par la veille
  (HTTP 404, mention « discontinued ») par la supposition d'un LLM 7B ;
- le nom et l'industrie du fabricant par la dernière variante reçue
  (« SIEMENS », industrie « electronique »…), le type d'un vendeur, le
  prix d'une offre par `null` quand le lot ne donne qu'un lien.

**Nouvelle politique** (`src/lib/ingest-pipeline.ts`) : une source ne peut
qu'enrichir. Champ absent ou vide → valeur en base conservée ; statut
remplacé seulement par `active`/`obsolete`, et jamais quand la veille a
tranché sur preuve (`lifecycleCheckedAt` renseigné et `needsReview` faux) ;
fabricants, catégories et vendeurs gardent le nom et le type de leur
création ; une offre sans prix garde le dernier prix relevé.

### 1.3 Recherche en scan complet

L'ancienne requête calculait `similarity()` et `to_tsvector()` sur **chaque
ligne** de `parts`, plus une sous-requête corrélée sur `part_references`,
à chaque recherche et à chaque frappe de l'autocomplétion.

Nouvelle implémentation (`src/lib/search/`) : les candidats viennent
uniquement d'index — btree (référence exacte), GIN `pg_trgm` (préfixe,
sous-chaîne, faute de frappe) sur `parts` et `part_references`, GIN sur une
colonne générée `parts.search_vector` (nom pondéré A, description B). Une
marque citée dans la requête (« Siemens 6ES7… ») est reconnue et donne un
bonus ; les fragments de référence sont pondérés par leur longueur ; le tri
se termine par l'id (pagination stable : l'ancien tri sur le seul score
pouvait dupliquer ou sauter des résultats entre deux pages).

Mesures sur 200 000 pièces (Postgres 16 local, meilleur de 3 essais) :

| Requête | Avant | Après | Remarque |
|---|---:|---:|---|
| `6ES7214-1AG40-0XB0` | 1 507 ms | 3 ms | |
| `Siemens 6ES7214-1AG40-0XB0` | 1 827 ms | 2 ms | score 5,8 → 13 : la marque n'est plus du bruit |
| `6ES7214` (préfixe) | 1 592 ms | 3 ms | |
| `PWRC1715WA` (tronquée) | 1 442 ms | 2 ms | |
| `variateur` (10 000 correspondances) | 1 659 ms | 62 ms | |
| `alimentation serveur` | 1 654 ms | 7 ms | |
| `zzzzzzzz` (aucun résultat) | 1 598 ms | 2 ms | |

Sur Neon (CPU partagé), l'ancienne requête devait être plus lente encore : le gain relatif devrait être du même ordre.

### 1.4 Sécurité

- `next` 15.5.19 → 15.5.28 (avis critiques : cache poisoning ISR, RCE via
  l'optimisation d'images, DoS Server Actions…), `drizzle-orm` 0.44 → 0.45.4
  (injection SQL par identifiants), `postcss` forcé en 8.5.31. Reste 4 avis
  modérés sur esbuild via `drizzle-kit` (outil de dev uniquement).
- `/admin/stats` et `/admin/review` étaient publiques (seul `robots.txt` les
  « cachait », en les listant). Authentification HTTP Basic dans le
  middleware (`ADMIN_USER` / `ADMIN_PASSWORD`) ; sans mot de passe, 404 en
  production.
- Clé API comparée à temps constant, logique d'auth centralisée
  (`requireApiKey`) au lieu de 5 copies.
- Paramètres `limit`/`offset` non validés : `limit=-5` ou `offset=abc`
  provoquaient des erreurs 500. Validation bornée (`src/lib/params.ts`).
- Limitation de débit : compteur auparavant partagé entre tous les
  endpoints (30 comparaisons bloquaient la recherche en lot), aucune limite
  sur la recherche, mémoire jamais purgée. Désormais un compteur par
  endpoint, purge bornée, limites sur recherche, autocomplétion, API v1,
  exports.
- `PATCH /api/repair/offers` choisissait la pièce par référence seule (au
  hasard entre fabricants) et le vendeur par sous-chaîne (« RS » →
  « ServerSupply »). Fabricant pris en compte (409 si ambigu), vendeur par
  slug exact puis préfixe de nom.

### 1.5 Bugs visibles des utilisateurs

- **Filtres de `/recherche` inopérants** : en production, un clic sur
  « Fabriquées », « Industrie »… lançait la requête mais la navigation ne
  s'appliquait jamais (reproduit de façon déterministe avec
  `router.push`, y compris sur la version d'origine). Cause : le
  `loading.tsx` de cette route, avec Next 15.5. Supprimé — la recherche
  répond maintenant en quelques millisecondes. Après « Charger plus », un
  changement de filtre gardait aussi les résultats de la recherche
  précédente (corrigé par une `key`).
- **Images Open Graph des pièces** : `/api/og/...` plantait à chaque appel
  (élément à deux enfants sans `display: flex`, refusé par Satori) — aucun
  aperçu lors d'un partage.
- « Tout ajouter à ma liste » (recherche en lot) **retirait** les pièces
  déjà suivies (bascule au lieu d'ajout).
- « Charger plus » depuis `?page=N` repartait de la page 2.
- Boutons « Ma liste » / « Comparer » imbriqués dans un lien (HTML
  invalide, navigation clavier et lecteurs d'écran) : carte en « lien
  étiré ».
- Logo cassé quand le service de favicons est bloqué (proxy d'entreprise,
  bloqueur) : l'erreur survenait avant l'hydratation et n'était jamais
  captée.
- Deux encarts d'alerte empilés sur une pièce obsolète remplacée.
- `specs` (enrichissement Gemini) et `datasheetUrl` stockés mais jamais
  affichés.
- Dates calculées dans le fuseau du serveur (UTC) : décalage d'un jour la
  nuit et risque d'erreur d'hydratation. Fuseau Europe/Paris fixé.
- Exports CSV : accents cassés dans Excel (pas de BOM UTF-8), échappement
  incomplet côté client (injection de formules possible), prix et devise
  appariés au hasard dès qu'une pièce avait des offres en plusieurs devises.

### 1.6 SEO

- JSON-LD : `discontinued` n'existe pas dans schema.org (→
  `availability: Discontinued`) et `lowPrice` mélangeait les devises.
- Sitemap : `lastModified = maintenant` sur chaque URL (Google ignore alors
  le champ) et hubs marque/catégorie vides inclus.

## 2. Ce qui a changé dans le code

- **Recherche** : `query-parser.ts` (marque, termes de référence pondérés),
  `postgres-search.ts` (candidats indexés), `searchOptionsFromParams()`.
  Le repli `ILIKE` (scan complet) est supprimé : la sous-chaîne est
  couverte par l'index trigramme.
- **Ingestion** : validation séparée (`ingest-validation.ts`), une
  transaction par pièce (pièce, cross-refs et offres en tout ou rien),
  écritures groupées, cache des identifiants par lot, résolution des
  relations en base, `warnings` dans la réponse, lots plafonnés à 500.
  Veille : un seul `UPDATE … RETURNING` par pièce.
- **Schéma** : colonne générée `search_vector`, index GIN (trigramme ×2,
  plein texte), index `(manufacturer_id, slug)` pour les URLs de fiche,
  `updated_at`, `supersessions.new_part_id`, `offers.seller_id`. Les enums
  Postgres sont dérivés des listes du contrat (`ingest-types.ts`).
- **Partagé** : `format.ts`, `csv.ts`, `part-export.ts`,
  `getCheapestOffers()` — cinq copies de `formatPrice` et deux d'export
  supprimées, trois requêtes mortes retirées.
- **Scripts** : `accumulate.ts` importe le contrat et la normalisation au
  lieu de les recopier, lit `INGEST_URL` (défaut inchangé) et précise le
  fabricant dans ses PATCH ; `generate-catalog-sql.py` nomme ses colonnes
  (l'ancien `neon-catalog.sql` ne se chargeait pas sur une base créée par
  `db:push`) ; `neon-setup.sql`, redondant avec `npm run seed`, est retiré.
- **Dépôt** : `accumulate.log` (4 000 lignes) et `.accumulate-state.json`
  ne sont plus versionnés.
- **Qualité** : `tests/unit`, `tests/integration` (garde-fou : la base doit
  contenir « test » dans son nom), `.github/workflows/ci.yml`.

## 3. Changements de comportement à connaître

- Le statut d'une pièce vérifié par la veille ne peut plus être modifié par
  `/api/ingest` (y compris un push manuel) : seule la veille, ou une
  correction SQL, le change.
- Le nom d'un fabricant, d'une catégorie ou d'un vendeur n'est plus renommé
  par ingestion (corriger en base si besoin).
- L'export CSV par marque gagne une colonne `category` ; tous les CSV
  commencent par un BOM UTF-8.
- Une requête réduite à un nom de marque (« Siemens ») liste ses pièces.
- La page de recherche n'affiche plus de squelette de chargement.

## 4. Mise en production

1. Vercel → Settings → Environment Variables : ajouter `ADMIN_PASSWORD`
   (et `ADMIN_USER` si autre que « admin »).
2. Vérifier l'extension puis appliquer le schéma :
   `CREATE EXTENSION IF NOT EXISTS pg_trgm;` puis
   `DATABASE_URL="postgres://…" npm run db:push`. Opérations ajoutées : une
   colonne générée, sept index, suppression de l'index redondant
   `parts_manufacturer_idx`. Aucune donnée supprimée.
3. Mac mini, avant `git pull` : les fichiers d'exécution n'étant plus
   versionnés, Git refusera de les écraser s'ils ont changé localement.
   ```bash
   cp scripts/ingest/.accumulate-state.json /tmp/
   git checkout -- scripts/ingest/accumulate.log scripts/ingest/.accumulate-state.json
   git pull
   cp /tmp/.accumulate-state.json scripts/ingest/
   ```
   `accumulate.ts` utilise désormais `INGEST_URL` s'il est défini dans
   `.env` (il l'affiche au démarrage) : vérifier qu'il pointe bien sur la
   production.
4. Relancer un `--update --once` et vérifier dans la réponse que
   `partsUpdated` > 0 et `errors` vide.

## 5. Feuille de route recommandée

### À décider rapidement

- **Abonnements email** (`/liste`) : le formulaire promet « vous serez
  alerté en cas de changement de statut », mais aucun code n'envoie
  d'email. Les adresses sont stockées sans double opt-in ni
  désinscription (exposition RGPD). Soit implémenter (tâche planifiée
  Vercel, envoi transactionnel, lien de confirmation et de
  désinscription), soit retirer le formulaire.
- **Offres « Radwell » du mode `--update`** : chaque pièce reçoit un lien
  de recherche Radwell sans prix ; cela remplace l'URL produit d'une offre
  Radwell existante et gonfle les compteurs d'offres.

### Court terme

- Migrations versionnées (`drizzle-kit generate` + `migrate`) au lieu de
  `db:push` en production.
- Revalidation à la demande (`revalidatePath`) après ingestion et veille :
  une fiche peut aujourd'hui rester une heure obsolète.
- Mode `--clean` : passer par un endpoint dédié à `productUrl` plutôt que
  par `/api/ingest` (qui exige un nom de pièce, que le LLM peut inventer).
- Retirer des prompts les champs ignorés par l'API (`normalizedCategory`,
  `industrySector`) ou les intégrer au schéma.
- Limitation de débit partagée entre instances (Upstash) si le trafic
  augmente ; Content-Security-Policy ; ESLint.

### Moyen terme

- Découper `accumulate.ts` (2 100 lignes, 5 modes) en modules testables :
  sources LLM, découverte d'URL, distributeurs, modes.
- Fusionner `/technicien` et `/recherche-lot` (fonctionnalités en double).
- Alias de marques dans la recherche (Allen-Bradley → Rockwell Automation)
  et insensibilité aux accents (`unaccent`).
- Prix multi-devises : conversion pour comparer et trier.
- Sitemap shardé au-delà de 50 000 URLs (prévu par la roadmap du README).
- Next.js 16 (embarque un `postcss` à jour, fin de support de la 15).

### Long terme

- Moteur dédié (Meilisearch / Typesense) quand la tolérance aux fautes en
  texte libre ou le volume (> 1 M de pièces) le justifieront : l'interface
  `SearchService` le permet sans toucher aux pages.
- Comptes utilisateurs pour synchroniser liste de suivi et comparaisons
  entre appareils (aujourd'hui en `localStorage`).
